# 스테이지 시스템 재설계와 데이터 테이블 명세

- 날짜: 2026-11-18
- 상태: 승인됨. **웹에서 짓는다** (2026-11-18 기획자 결정: 고닷으로 옮겨 봤으나 화면이 웹과 너무 달라 웹으로 돌아왔다). 9절 "고닷 이식"은 따르지 않는다. 구현: `src/core/stage/`, `src/render/stageRenderer.ts`, `src/data/stages/`.
- 대신하는 것: `2026-11-17-validation-build-design.md` 의 5.4절(인게임 한 단위)과 맵·장치·보스 패턴의 구조. 박자 시계, 판정, 소리 합성, 비주얼 문법은 그대로 쓴다.

표기: **[결정]** 은 기획자가 정한 것, **[까미]** 는 설계자가 채운 제안(바꿔도 됨)이다.

## 1. 의도

검증 빌드는 "방마다 퍼즐 하나, 그 뒤에 보스"였다. 기획자가 의도한 것은 그게 아니다. **[결정]**

- 스테이지 하나는 **작은 단위의 메트로베니아 + 어드벤처**다. 하나로 이어진 맵 곳곳을 돌아다니며 전투와 기믹 회피로 파츠를 얻고, 보스로 향한다.
- 한 스테이지에서 **정해진 목숨**으로 맵을 탐험하는 재미가 있어야 한다. 한 지역을 돌며 여러 고비를 넘는 흐름이지, 보스를 늘리자는 것이 아니다.
- 맵은 직사각형으로 뭉뚱그리지 않는다. **동선과 배치 감각**을 고려해 짠다.
- 기믹은 지금보다 **다양**해야 한다.
- 전투의 중심은 **수호자**(파츠 앞의 짧은 대결)와 **장치**(길을 막는 박자 장치)다. **몬스터**도 있지만 장치처럼 쓰이는 방해물이다. 잡아서 성장하는 개념이 아니다.
- **핵심:** 파츠를 얻으러 가는 길과 그때의 전투가, 보스전에 필요한 기믹과 싸우는 방식을 **가르쳐야** 한다.
- 지금의 함정 구간은 **대시 거리와 무관하게** 짜여 있어서, 대시로 피하며 나아간다는 감각이 없고 오히려 불쾌하다. 고쳐야 한다.

이 문서는 그 구조를 세우고, 장치를 포함한 **데이터 테이블의 명세**를 정하고, **고닷 이식**을 어떤 순서로 할지 정한다.

## 2. 목표 / 비목표 / 반목표

**목표**

- 스테이지, 박자표, 맵, 장치·몬스터·수호자·보스를 **엔진과 무관한 데이터 파일**로 정의한다. 웹 프로토타입과 고닷이 같은 파일을 읽는다.
- 길에서 배운 것과 보스가 쓰는 것이 **같은 데이터**가 되게 한다.
- 맵의 모든 거리를 **플레이어의 몸(걸음과 대시)** 에서 나온 단위로 적는다.
- 데이터만으로 검사할 수 있는 것은 **자동으로 검사**한다(배웠는가, 닿을 수 있는가, 대시로 지나갈 수 있는가).
- 이 구조로 스테이지 하나를 다시 만들어 손맛을 재검증한다.

**비목표**

- 스테이지 여러 개, 스토리, 저장, 메뉴.
- 맵 편집기. 처음엔 데이터 파일을 손으로 쓴다.
- 성장, 경험치, 드롭, 상점.
- 자동 공격을 수동으로 바꾸는 일(따로 정한다).

**반목표** (돌아가도 실패)

- 보스가 길에서 한 번도 안 보여 준 것을 처음 들고나오는 것.
- 대시 거리와 무관한 함정. 지나갈 수는 있어도 리듬이 안 생기는 배치.
- 방을 복도로 이은 구조로 돌아가는 것.
- 적을 잡는 것이 목적이 되는 것.

## 3. 원칙

1. **보스에서 거꾸로 짠다.** 스테이지의 설계는 보스가 쓰는 모티프 목록에서 시작한다. 길과 수호자는 그 목록을 하나씩 가르치는 순서다. **[결정을 구조로 옮긴 것]**
2. **모티프 하나, 쓰임 여럿.** "어떤 박에 어떤 모양이 어떻게 떨어지는가"를 한 번만 정의하고, 장치·몬스터·수호자·보스가 같은 것을 가져다 쓴다. **[까미]**
3. **거리의 단위는 몸의 단위다.** 맵과 모양의 길이는 픽셀이 아니라 걸음과 대시에서 나온 단위로 적는다(5절). **[결정을 구조로 옮긴 것]**
4. **데이터는 엔진을 모른다.** 좌표, 박, 조건만 있고 그리는 법이나 엔진 고유의 것은 없다. **[까미]**

## 4. 만드는 방법 — 검토한 길

**데이터의 짜임**

| 길 | 얻는 것 | 치르는 값 |
|---|---|---|
| **모티프 중심** | 배움과 쓰임이 같은 데이터. "보스가 쓰는 것이 길에 먼저 나왔는가"를 자동 검사 | 모티프의 틀을 처음에 잘 잡아야 함 |
| 종류별 표(장치 표, 몬스터 표, 보스 표…) | 쉽고 바로 시작 | 같은 기믹을 표마다 다시 적음. 학습 여부는 사람이 챙김 |
| 스테이지별 대본 | 가장 자유로움 | 표가 아니라 코드에 가까워져 명세와 이식이 어려움 |

**맵의 짜임**

| 길 | 얻는 것 | 치르는 값 |
|---|---|---|
| **도형 맵**(원, 캡슐, 다각형을 이어 붙임) | 네모를 벗어난 동선. 지금 비주얼(가는 선으로 그린 땅)과 맞음. 고닷의 다각형 충돌로 그대로 옮겨짐 | 타일 충돌과 방 풀이 봇을 다시 짬 |
| 타일 맵 유지 | 바꿀 것이 적음 | 곡선과 사선이 계단이 되고 네모의 느낌이 남음 |

**선택: 모티프 중심 + 도형 맵. [까미의 추천. 기획자가 이 문서를 승인하면 확정]**

## 5. 거리의 체계

지금의 문제: 문짝의 폭(32px), 문짝 사이(96px), 틈(64px)이 대시 거리(정확 170 / 근접 120 / 빗나감 50px)나 한 박에 걷는 거리(110 BPM에서 120px)와 아무 관계가 없다. 대시하면 다음 함정 위에 떨어지고, 걸어서 지나는 게 정답이 된다.

**단위 [까미]**

- **1U = 한 박 동안 걷는 거리.** `걷는 속도 × 한 박의 길이`. 스테이지의 템포가 바뀌면 U의 픽셀 값도 바뀐다.
- **대시 거리는 U의 배수로 정한다.** 근접 = 1U, 정확 = 1.4U, 빗나감 = 0.4U. (지금 수치가 110 BPM에서 우연히 거의 이 비율이다.) 그래서 "한 박에 한 번 대시"와 "한 박에 한 걸음"이 같은 길이가 되고, 걷기와 대시를 섞어도 박이 어긋나지 않는다.
- 맵의 좌표, 모양의 크기, 사거리는 모두 U로 적는다.

**배치의 규칙 [까미]**

| 무엇 | 규칙 | 이유 |
|---|---|---|
| 대시로 뚫는 위험의 두께 | 0.5U 이하 | 근접 대시(1U)로 지나면 앞뒤로 0.25U씩 남는다 |
| 대시로만 건너는 틈의 폭 | 0.6U ~ 0.8U | 빗나간 대시(0.4U)로는 못 건너고, 근접(1U)으로는 여유 있게 건넌다 |
| 대시 뒤에 내려설 땅 | 위험 끝에서 0.5U 이상 | 정확 대시(1.4U)로 가도 다음 위험에 떨어지지 않는다 |
| 잇따른 대시 위험 사이 | 1U 또는 2U (박의 정수배) | 대시-걸음-대시가 박에 맞는다 |
| 걸어서 타이밍 맞추는 위험 | 통과 시간이 박의 1/2 이하 | 한 박 안에 들어가서 나올 수 있다 |

이 규칙은 검사기가 데이터에서 자동으로 확인한다(7절).

## 6. 데이터 테이블 명세

파일은 JSON이고 `data/` 아래에 둔다. 길이는 U, 시간은 스텝(박을 나눈 가장 작은 단위)이다. 아래는 표마다의 필드다. 세부 이름은 구현하며 다듬되, 뜻은 바꾸지 않는다.

### 6.1 `stage` — 스테이지

| 필드 | 뜻 |
|---|---|
| `id`, `group` | 식별자, 스테이지 묶음(팔레트와 장르를 묶음 단위로 정한다) |
| `palette` | rust / mid / navy / ochre **[결정: 묶음마다 바꿔 낌]** |
| `meter` | 6.2 |
| `bpm`, `songSeed` | 템포, 곡의 씨앗값 |
| `lives` | 이 스테이지의 목숨 수. 악기를 얻으면 가득 회복된다 **[결정]** |
| `map` | 6.5 |
| `parts` | 6.7 |
| `placements` | 6.6의 방출원을 맵에 놓은 목록 |
| `gates` | 6.8 |
| `encounters` | 6.9 수호자 대결 |
| `boss` | 6.10 |
| `checkpoints` | 되살아나는 자리들(세이브가 아니다. 세이브는 악기를 얻는 순간) |

### 6.2 `meter` — 박자표

지금은 4/4와 마디당 16스텝이 코드에 박혀 있다. 레벨마다 박자가 다를 수 있으므로 데이터로 뺀다. **[결정: 4/4 아닌 박자, 저지 클럽, 브레이크비트 가능]**

| 필드 | 뜻 |
|---|---|
| `stepsPerBeat` | 박을 몇으로 나누는가 (보통 4) |
| `beatsPerBar` | 마디의 박 수 (4, 3, 5, 7…) |
| `dodgeSteps` | 마디 안에서 **회피의 기준이 되는 스텝들**(회피의 격자). 처음 할 때는 챕터의 것, 하드 모드에서는 낀 드럼의 것(10b절). 킥과 스네어가 울리는 자리. 4/4면 `[0,4,8,12]`, 저지 클럽이면 킥의 불규칙한 자리 **[결정: 회피는 킥/스네어 박에]** |
| `strikeSteps` | 적의 타격이 떨어질 수 있는 스텝들(타격의 격자). 언제나 챕터의 것 |

### 6.3 `layer` — 악기 겹

| 필드 | 뜻 |
|---|---|
| `id` | drum, hat, bass… 스테이지마다 다를 수 있다 |
| `role` | `part`(모으는 것) / `lead` / `pad` |
| `pattern` | 겹의 소리: 곡 생성 규칙의 이름과 매개변수. 스테이지가 기본값을 준다(10b절) |
| `attack` | 플레이어가 이 악기를 들었을 때의 자동 공격: 나가는 스텝, 사거리(U), 피해 |
| `opens` | 이 악기로 여는 것들의 표식(6.8) |

### 6.4 `motif` — 모티프

이 설계의 중심. 한 번의 공격이 아니라 **되풀이되는 리듬 형태**다.

| 필드 | 뜻 |
|---|---|
| `id`, `layer` | 식별자, 어느 겹에 실리는가(색과 여운이 이걸 따른다) |
| `shape` | 모양과 크기(U): `circle`, `ring`, `band`, `fan`, `rect`, `halfplane` |
| `anchor` | 모양의 기준: `self`(내보내는 쪽), `target`(플레이어의 예고 시작 때 자리), `fixed`(맵 좌표) |
| `period` | 되풀이 주기(스텝) |
| `hits` | 주기 안에서 타격이 떨어지는 자리. 절대 스텝이 아니라 **몇 번째 타격 자리인가**(`strikeSteps` 의 순번)로 적는다. 격자가 바뀌면 모티프가 따라간다(10b절) |
| `telegraph` | 예고 길이(스텝) |
| `hold` | 머무는 길이(스텝). 0보다 크면 머무는 동안 **박자마다** 다시 판정 **[결정]** |
| `answer` | 이걸 넘기는 방법: `dash`(박자 대시로 뚫음) / `walk`(걸어서 벗어남) / `wait`(안전한 곳에서 기다림). 규칙이 아니라 설계자와 검사기를 위한 표시다 |
| `teaches` | 무엇을 가르치는가, 한 줄(설계자를 위한 글) |

**타격을 넘기는 규칙은 하나다.** 길의 장치든 보스든 같다. 타격이 떨어지는 순간에 (가) 모양 밖에 있거나, (나) 회피의 무적 안에 있으면 넘긴 것이다.

**회피의 무적 [결정]**

| 판정 | 무적 |
|---|---|
| 저스트(정확) | 회피하는 동안 내내 |
| 그 밖 | 누르는 순간부터 아주 짧은 시간만 |

그래서 저스트가 아니면 **대시로 모양을 실제로 빠져나와야** 한다. 대시 거리와 함정의 두께(5절)가 여기서 의미를 갖는다. 저스트는 그 거리의 부담을 덜어 주는 보상이다.

- 저스트가 아닐 때의 무적 길이는 조절값으로 두고 0.05초 안팎에서 시작한다. **[까미]**
- 저스트의 판정 창은 박의 앞뒤로 열려 있으므로, 박보다 조금 늦게 눌러도 저스트면 그 박의 타격을 넘긴 것으로 친다. 이를 위해 피해는 박이 아니라 저스트 창이 닫힐 때 확정한다. **[까미]**
- 머무는 타격은 박마다 다시 떨어지므로 회피 한 번으로는 버틸 수 없고, 걸어서 벗어나야 한다.
- 지금 빌드는 근접 판정에도 긴 무적을 주고, 방의 장치와 보스가 서로 다른 규칙을 쓴다. 이 규칙 하나로 바꾼다.

**같은 모티프라도 쓰는 자리마다 달라질 수 있다. [까미]** 놓을 때 `rot`(돌림), `scale`(0.5~2배), `mirror`(뒤집음), `phase`(어긋남)를 줄 수 있고, 그래도 같은 모티프로 센다. "배웠는가"는 모티프의 id로 본다.

### 6.4b `figure` — 악형

모티프 몇 개를 정해진 간격으로 이은 짧은 묶음. 안에서 밖으로 차례로 퍼지는 고리 셋, 돌아가며 떨어지는 빔 같은 것이다. 악형도 id를 갖고, 장치·수호자·보스가 같은 악형을 가져다 쓴다. "배웠는가"는 악형의 id로도 본다. **[까미]**

| 필드 | 뜻 |
|---|---|
| `id` | 식별자 |
| `steps` | `{ at(스텝), motif, rot, scale, mirror }` 의 목록 |
| `length` | 전체 길이(스텝) |

### 6.5 `map` — 도형 맵

| 필드 | 뜻 |
|---|---|
| `ground` | 땅을 이루는 도형들: `circle{x,y,r}`, `capsule{x1,y1,x2,y2,r}`, `rect{x,y,w,h,rot}`, `polygon{points}`. 겹치면 하나의 땅이다 |
| `holes` | 땅에서 파낸 도형들(낭떠러지) |
| `regions` | 이름 붙인 구역: 음악 미리듣기, 대결장, 구도선 같은 것의 기준 |
| `routes` | 구역과 구역을 잇는 길의 목록: `{ from, to, via(지나는 문이나 없음) }`. 가는 방향이 있는 그래프다. 검사기는 길을 짐작하지 않고 이것을 읽는다 **[까미]** |
| `start` | 시작 자리 |

땅이 아닌 곳은 모두 죽는 땅이다.

### 6.6 `emitter` — 방출원

모티프를 내보내는 것. 장치, 몬스터, 수호자, 보스가 모두 이 표의 한 줄이다.

| 필드 | 뜻 |
|---|---|
| `id`, `kind` | `device`(고정 장치) / `monster`(움직이는 방해물) / `guardian` / `boss` |
| `motifs` | 내보내는 모티프들과 각자의 위상(몇 스텝 어긋나는가) |
| `motion` | `none` / `path`(정해진 길을 박에 맞춰) / `orbit` / `approach`(박마다 한 걸음 다가옴) |
| `body` | 몸의 크기(U). 닿으면 다치는가 |
| `health` | 0이면 부술 수 없다. 부술 수 있으면 체력과 `weakTo`(잘 듣는 악기) |
| `onBreak` | 부서질 때 일어나는 일: 없음 / 표식을 켬(문이 열림 등) |

몬스터는 `motion` 이 있는 장치일 뿐이다. 잡아도 얻는 것은 길뿐이다. **[결정: 방해 장치로서의 몬스터]**

### 6.11 목숨, 세이브, 되살아남

**결정 [기획자]**

- 스테이지마다 정해진 목숨으로 탐험한다.
- **악기를 얻는 순간이 세이브다.** 그때 목숨이 회복되고, 그 상태가 저장된다.
- 이 세이브는 스테이지 안에서만 산다. 스테이지를 나가면 남지 않는다.
- 맞거나 떨어지면 가루로 흩어졌다가 2박 뒤에 다시 뭉친다.

**채운 것 [까미]**

- 맞거나 떨어지면 목숨 하나를 잃고, 가장 가까운 지나온 `checkpoint` 에서 뭉친다. `checkpoint` 는 되살아나는 자리일 뿐 세이브가 아니다. 대결장의 입구와 긴 구간의 사이에 둔다.
- **목숨이 0이 되면 마지막 세이브로 돌아간다.** 마지막으로 악기를 얻은 자리에서, 그때의 목숨과 그때까지 얻은 악기, 그때 열려 있던 문과 부순 장치의 상태로 다시 시작한다. 악기를 하나도 못 얻었으면 스테이지의 처음이다.
- 대결 중에 목숨을 잃으면 대결장 입구에서 뭉치고, 상대의 체력은 그대로 두되 지금 악구를 처음부터 다시 한다. 목숨이 0이 되어 세이브로 돌아가면 그 대결은 처음부터다.
- 지금 빌드는 방에서 떨어져도 목숨이 안 깎이고, 보스전에서만 체력 셋을 쓴다. 이것을 스테이지 전체의 목숨 하나로 합친다.

## 7. 자동 검사 **[까미]**

데이터를 읽을 때 아래를 확인하고, 어기면 어디가 왜 틀렸는지 말한다.

검사기는 맵의 모양에서 동선을 짐작하지 않는다. 설계자가 적은 `routes`(6.5)를 따라간다.

| 검사 | 내용 |
|---|---|
| 배웠는가 | 보스 악구가 쓰는 모든 모티프가, 보스 문에 닿기 전의 길(장치나 몬스터)에 한 번 이상, 수호자 대결에 한 번 이상 나온다 |
| 닿는가 | 시작 자리에서 문의 조건을 차례로 채우며 모든 파츠와 보스에 닿는 순서가 하나 이상 있다 |
| 박에 맞는가 | 모든 `hits` 가 `strikeSteps` 위에 있다 |
| 몸에 맞는가 | `answer: dash` 인 위험과 틈이 5절의 규칙을 지킨다 |
| 숨 쉴 곳 | 위험이 잇따르는 구간 사이에 위험 없는 땅이 있다 |

"지나갈 수 있는가"를 봇으로 확인하는 테스트는 유지하되, 봇이 걷기뿐 아니라 **대시를 박에 맞춰 쓰는 길**로 통과하는지 본다.

## 8. 지금 코드에서 남는 것과 바뀌는 것

| 남는 것 | 바뀌는 것 |
|---|---|
| 박자 시계, 예약 재생, 회피 판정과 지연 보정 | 4/4 고정 → `meter` 데이터 |
| 소리 합성, 겹 믹스, 지휘자(악구 진행) | 타일 맵 → 도형 맵과 도형 충돌 |
| 2박 되살아남, 조절값의 틀 | 칸 글자에 묶인 장치 규칙 → 모티프와 방출원 |
| 비주얼 문법(면은 지금, 선은 여운, 두 색 계열) | 보스 패턴 코드 → 데이터 |
| | 방마다 다른 실패 규칙 → 스테이지 단위 목숨 |

보스의 공격과 길의 장치가 **하나의 공격 엔진**으로 합쳐진다. 지금은 따로 짜여 있다.

## 9. 고닷 이식

- **지금 웹 코드를 한 줄씩 옮기지 않는다.** 바뀔 구조를 옮기는 일이 된다.
- **먼저 할 것은 고닷의 소리 확인이다.** 이 게임에서 가장 틀어지기 쉬운 것이 실시간 합성과 박의 정확도인데, 고닷에서 그게 되는지 아직 모른다. 작은 실험 하나로 확인한다: 고닷에서 합성한 소리가 박에 맞게 나고, 입력 판정이 어긋나지 않는가. 이 결과에 따라 합성을 고닷 안에서 할지, 미리 구운 소리를 쓸지가 갈린다. **[까미: 이식의 가장 큰 위험이라 가장 먼저]**
- 그다음 이 문서의 데이터 파일을 읽는 고닷 쪽 구현을 새로 짓는다. 웹의 테스트(판정, 검사기, 공격 엔진의 규칙)가 고닷 구현의 정답지가 된다.
- 고닷의 버전, 언어(GDScript / C#)는 소리 실험에서 함께 정한다.

## 10. 순서 **[까미]**

1. 이 문서의 승인.
2. 웹에서: `meter` 데이터화 → 도형 맵과 충돌 → 모티프·방출원 엔진 → 검사기 → 스테이지 단위 목숨.
3. 새 구조로 스테이지 하나를 다시 만든다. **이 스테이지는 4/4다.** 박자표는 데이터로 빼 두되, 불규칙한 박에서의 거리 규칙과 판정은 이번 범위가 아니다(5절의 규칙은 박이 고른 경우만 다룬다). (맵의 실제 설계는 레벨디자인 세션과 함께). 기획자가 손맛을 본다. 특히 대시로 피하며 나아가는 감각.
4. 2와 나란히: 고닷 소리 실험.
5. 고닷에서 새로 짓기.

## 10b. 챕터와 악기 세트

스테이지 밖의 구조. 지금 만들지는 않지만 데이터의 모양에 영향을 주므로 여기에 정해 둔다.

**결정 [기획자]**

- **챕터는 드럼 박자를 중심으로 묶는다.** 킥과 스네어의 조합, 장르가 가진 박자가 묶음의 기준이다. 스윙, 포 온 더 플로어, 브레이크비트, 저지 클럽, 4/4 킥+스네어는 서로 다른 챕터다.
- **챕터를 다 깨면 그 챕터의 악기 세트를 장비로 얻는다.**
- **이미 깬 스테이지는 장비를 바꿔서 다시 할 수 있다. 이것이 하드 모드다.**

처음 할 때는 스테이지가 준비한 온전한 음악을 듣고, 다시 할 때는 조합의 재미와 어려움을 얻는다.

**데이터 [까미]**

`chapter` — 챕터

| 필드 | 뜻 |
|---|---|
| `id`, `title` | 식별자, 이름 |
| `meter` | 이 챕터의 판정 격자(6.2). 챕터 안의 스테이지는 모두 이것을 쓴다. 6.1의 `stage.meter` 는 챕터에서 물려받는다 |
| `palette` | 챕터의 팔레트. 6.1의 `stage.group` 이 곧 챕터다 |
| `instrumentSet` | 이 챕터의 악기 세트. 챕터를 다 깨면 장비로 풀린다 |
| `stages` | 스테이지들의 순서 |

`instrumentSet` — 악기 세트

| 필드 | 뜻 |
|---|---|
| `id` | 식별자 |
| `layers` | 드럼·하이햇·베이스 각각의 **겹의 소리**(`pattern`, 음색)와 **플레이어의 공격 박자**(`attack`) |

이를 위해 지금 한 덩어리로 붙어 있는 셋을 데이터에서 갈라 둔다.

| 무엇 | 뜻 | 누구의 것 |
|---|---|---|
| **판정의 격자** | 회피의 기준 박, 적의 타격이 떨어질 수 있는 자리 | 챕터(`meter`) |
| **겹의 소리** | 그 악기가 실제로 내는 리듬과 음색 | 악기 세트. 처음 할 때는 그 챕터의 세트 |
| **플레이어의 공격 박자** | 든 악기로 공격이 나가는 자리 | 악기 세트 |

모티프의 타격 자리(`hits`)는 절대 스텝이 아니라 **"몇 번째 타격 자리인가"** 로 적는다. 챕터의 격자가 다르면 같은 모티프가 그 격자를 따라간다.

**하드 모드에서 판정의 격자는 낀 드럼을 따른다. [결정]** 다른 챕터의 악기 세트를 끼면 회피할 수 있는 박 자체가 바뀐다. 스테이지의 타격은 원래 자리에 그대로 떨어지므로, 내 회피 박과 안 맞는 타격은 저스트로 넘길 수 없고 대시의 거리로 빠져나가거나 걸어서 피해야 한다.

따라오는 것 **[까미]**

- 판정의 격자가 둘이 된다: **타격의 격자**(스테이지와 챕터의 것, 맵과 모티프가 따름)와 **회피의 격자**(낀 드럼의 것). 처음 할 때는 둘이 같다. 데이터와 코드에서 처음부터 둘로 나눠 둔다.
- 회피의 격자가 달라도 5절의 거리 규칙은 그대로다. 맵은 타격의 격자에 맞춰 짜여 있고, 대시의 거리는 판정과 무관하게 나간다.
- 하드 모드에서 깰 수 있는지는 스테이지와 악기 세트의 조합마다 다르다. 검사기가 조합마다 "회피 박과 겹치지 않는 타격"을 세어 보고서로 내고, 그런 타격이 모두 거리로 빠져나가거나 걸어서 피할 수 있는 것인지 확인한다. 못 깨는 조합은 막거나 표시한다.

## 11. 열려 있는 것

- **대시 거리를 템포에 묶을지.** 5절은 "근접 대시 = 한 박 걸음"으로 묶자고 제안한다. 느린 곡에서는 대시가 길어진다. 손맛을 보고 정한다.
- **파츠가 꼭 악기인지.** 악기가 아닌 파츠(문을 여는 열쇠 같은 것)도 있는지.
- **악기가 길을 여는 구조를 쓸지.** 제안일 뿐이다.
- **목숨이 0일 때 돌아가는 세이브의 범위.** 6.11은 "마지막으로 악기를 얻은 때의 상태 전부"로 적었다.
- **대결 중에 목숨을 잃었을 때.** 6.11은 "입구에서 뭉치고, 상대의 체력은 그대로, 지금 악구만 처음부터"로 적었다.
- **스테이지 하나의 크기와 길이.** 탐험이라 부를 만한 최소 크기.
- **자동 공격.** 장치를 부수는 일이 생기면 자동 공격으로 충분한지.
- **몬스터의 움직임 종류.** 6.6의 넷으로 충분한지.
