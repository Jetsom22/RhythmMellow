# 레벨 디자인 작업대로서의 웹 (초안)

- 날짜: 2026-11-18
- 상태: 초안. 누가 무엇을 만드는지는 기획자 확인 대기.
- 근거: 기획자 결정 — 웹 빌드를 **프로토타이핑과, 고닷에 옮기기 전의 레벨 디자인을 하는 곳**으로 만든다.

레벨 디자인의 흐름은 이렇다. 데이터 파일(`data/`)을 쓴다 → 웹이 읽어 그리고 검사하고 봇을 돌린다 → 기획자가 Pages에서 보고 쥐어 본다 → 고친다. 같은 파일이 나중에 고닷으로 간다. 웹은 그 사이에서 **보여 주고, 검사하고, 쥐어 보게 하는 곳**이다.

## 갖춰야 할 것 [까미]

우선순위 순.

| # | 무엇 | 왜 |
|---|---|---|
| 1 | **스테이지를 데이터로 열기.** `?stage=stage-01` | 맵을 코드가 아니라 파일로 바꾸려면 |
| 2 | **어디서든 시작.** `?at=<체크포인트>&parts=drum,hat` | 기획자가 고친 자리만 바로 쥐어 본다. 지금의 `?skip=boss` 를 일반화한 것 |
| 3 | **검사 보고서.** 배웠는가, 첫 만남, 반복, 닿는가, 박에 맞는가, 몸에 맞는가, 숨 쉴 곳. 통과·실패와 맵 위의 자리 | 기획자와 레벨 세션 둘 다 손으로 못 확인하는 것을 데이터로 확인 |
| 4 | **지도 보기.** 도형 맵 전체를 U 격자 위에. 구역 이름, 길의 그래프, 문의 조건, 체크포인트, 방출원 | 클라우드 세션은 화면을 못 본다. 지도가 Pages에 있어야 같이 본다 |
| 5 | **박 넘기기.** 지도 위에서 한 마디를 스텝 단위로 넘기며 예고와 타격의 자리를 본다 | 배치가 박에 맞는지 눈으로 |
| 6 | **봇의 발자국.** 봇이 지나간 길을 지도 위에 선으로, 대시한 자리에 점으로 | "풀 수 있다"를 기획자가 직접 본다 |
| 7 | **가르침 지도.** 모티프마다 첫 만남 → 반복 → 수호자 → 보스의 자리를 표로, 데이터에서 자동으로 | 학습 → 반복 → 심화가 지켜지는지 한눈에 |
| 8 | 데이터를 고치면 바로 다시 그림(개발 서버) | 고쳐서 다시 보는 횟수 |

## 나누는 법 (제안) [까미]

| 무엇 | 누가 | 이유 |
|---|---|---|
| 1·2·3 — 데이터 읽기, 시작 자리, 검사기 | 시스템 | 명세 10절 2의 일과 같다. 게임 규칙의 일부 |
| 4·5·6·7 — 지도 보기, 박 넘기기, 발자국, 가르침 지도 | 레벨디자인 | 게임과 따로 도는 보기 전용 페이지(`workbench.html`, `src/workbench/**`). 게임 규칙과 그리기를 건드리지 않고 데이터와 검사 결과를 읽기만 한다 |
| 지도 보기의 그림 문법 | 아트에 확인 | 게임과 같은 색 체계를 쓰되, 작업대는 개발 도구라 다듬지는 않는다 |
| 데이터 파일 `data/stages/*.json` | 레벨디자인 | 맵과 배치는 레벨의 영역 |

기획자가 이렇게 나누는 데 동의하면 `docs/handoff/README.md` 의 영역 표에 `src/workbench/**`, `workbench.html`, `data/stages/**` 를 레벨디자인 쪽으로 올린다(그 표는 시스템 세션이나 기획자가 고친다).
