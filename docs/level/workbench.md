# 레벨 디자인 작업대로서의 웹 (초안)

- 날짜: 2026-11-18
- 상태: 초안. 누가 무엇을 만드는지는 기획자 확인 대기(명세가 "고닷에서 바로"로 승인된 뒤의 상황은 아래 "나누는 법").
- 근거: 기획자 결정 — 웹 빌드를 **프로토타이핑과, 고닷에 옮기기 전의 레벨 디자인을 하는 곳**으로 만든다.

레벨 디자인의 흐름은 이렇다. 데이터 파일(`data/`)을 쓴다 → 웹이 읽어 그리고 검사하고 봇을 돌린다 → 기획자가 Pages에서 보고 쥐어 본다 → 고친다. 같은 파일이 나중에 고닷으로 간다. 웹은 그 사이에서 **보여 주고, 검사하고, 쥐어 보게 하는 곳**이다.

## 갖춰야 할 것 [까미]

우선순위 순.

| # | 무엇 | 왜 |
|---|---|---|
| 1 | **스테이지를 데이터로 열기.** `?stage=stage-01` | 맵을 코드가 아니라 파일로 바꾸려면 |
| 2 | **어디서든 시작.** `?at=<체크포인트>&parts=drum,hat` | 기획자가 고친 자리만 바로 쥐어 본다. 지금의 `?skip=boss` 를 일반화한 것 |
| 3 | **검사 보고서.** 배웠는가, 첫 만남, 반복, 닿는가, 박에 맞는가, 몸에 맞는가, 숨 쉴 곳. 통과·실패와 맵 위의 자리 | 기획자와 레벨 세션 둘 다 손으로 못 확인하는 것을 데이터로 확인 |
| 4 | **지도 보기.** 도형 맵 전체를 U 격자 위에. 구역 이름, 길의 그래프, 문의 조건, 체크포인트, 장치·몬스터·수호자 | 클라우드 세션은 화면을 못 본다. 지도가 Pages에 있어야 같이 본다 |
| 5 | **박 넘기기.** 지도 위에서 한 마디를 스텝 단위로 넘기며 예고와 타격의 자리를 본다 | 배치가 박에 맞는지 눈으로 |
| 6 | **봇의 발자국.** 봇이 지나간 길을 지도 위에 선으로, 대시한 자리에 점으로 | "풀 수 있다"를 기획자가 직접 본다 |
| 7 | **가르침 지도.** 토막마다 첫 만남 → 반복 → 수호자 → 보스의 자리를 표로, 데이터에서 자동으로 | 학습 → 반복 → 심화가 지켜지는지 한눈에 |
| 8 | 데이터를 고치면 바로 다시 그림(개발 서버) | 고쳐서 다시 보는 횟수 |

## 나누는 법 — 기획자 확인 대기

**2026-11-18 상황이 바뀌었다.** 명세가 승인되면서 순서가 바뀌었다: 시스템 세션은 새 구조를 **고닷에서 바로 짓고**, 10절의 "웹에서 먼저"는 따르지 않는다(명세의 상태 줄). 웹 프로토타입은 "규칙의 정답지로 남긴다"(`godot/README.md`).

그런데 기획자가 레벨디자인 세션에 준 방향은 **웹을 프로토타이핑과 고닷 전 레벨 디자인의 자리로 만든다**는 것이다. 둘을 함께 지키려면 위 1~8을 웹에서 누가 짓는지 정해야 한다. 데이터 읽기, 도형 맵, 패턴 엔진, 검사기가 웹에 있어야 작업대가 된다.

| 안 | 웹의 1~3(데이터, 시작 자리, 검사기)과 도형 맵·패턴 엔진 | 웹의 4~8(지도 보기, 박 넘기기, 발자국, 가르침 지도) | 치르는 값 |
|---|---|---|---|
| **가. 레벨디자인이 웹 작업대를 통째로** | 레벨디자인 | 레벨디자인 | 레벨 세션이 `src/core` 의 규칙까지 손댄다. 고닷과 웹의 규칙이 어긋나지 않게 같은 데이터 파일과 같은 검사 표를 정답지로 둔다 |
| 나. 시스템이 웹에도 짓는다 | 시스템 | 레벨디자인 | 시스템 세션이 고닷과 웹 두 곳을 짓는다 |
| 다. 작업대도 고닷으로 | 고닷 | 고닷(웹 내보내기로 Pages에) | 웹 프로토타입은 멈춘다. 레벨 세션은 데이터만 쓴다 |

까미의 생각: 기획자의 말("우린 기존 웹 쪽 개발해서")이 **가**를 뜻한다면, 레벨디자인이 `data/stages/**`, `src/workbench/**`, 그리고 웹의 도형 맵·패턴·검사기를 맡는다. 이 경우 `docs/handoff/README.md` 의 영역 표를 고쳐야 하고, 그 표는 기획자나 시스템 세션이 고친다.
